# Lesson 1 · Named Templates & `_helpers.tpl` in Depth

Lesson 4 showed you `_helpers.tpl` exists. Now you'll actually use it — the standard place charts put small, reusable snippets of template logic instead of repeating them (or hardcoding values) in every manifest.

## `define` and `include`

A named template is declared with `define` and rendered elsewhere with `include`:

```
{{- define "webapp.name" -}}
{{- .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}
```

```yaml
metadata:
  name: {{ include "webapp.name" . }}
```

A few things about this that trip people up the first time:

- **`define`/`end` blocks produce no output where they're declared** — they just register the template under that name for later use, so it's safe to put them anywhere, but by convention they all live in `_helpers.tpl`. The leading underscore tells Helm "this isn't a Kubernetes manifest, don't try to render it as a standalone document."
- **`include` vs `template`**: both render a named template, but `include` is a function (its output can be piped, e.g. `{{ include "webapp.labels" . | nindent 4 }}`), while `template` is an action that can't be piped. Use `include` — it's what you'll see in nearly every real-world chart.
- **The dot (`.`) is the top-level context** (values, release info, chart info). A named template only sees what you explicitly pass it — `include "webapp.name" .` passes the whole context down; forgetting the trailing `.` is a common source of `nil pointer` template errors.
- **Whitespace control** (`{{-` / `-}}`) trims the newline/whitespace on that side of the tag. Without it, every `define`/`end` line leaves blank lines in the rendered output — usually harmless for YAML, but it gets noisy fast in a chart with a dozen helpers.

## The naming convention

Charts generated by `helm create` (and virtually every published chart) follow this pattern, which you'll reproduce by hand this lesson:

| Helper | Purpose |
|---|---|
| `<chart>.name` | The short base name, usually just `.Chart.Name` |
| `<chart>.fullname` | A resource-name prefix combining release + chart name, so two installs of the same chart in the same namespace don't collide |
| `<chart>.labels` | The full set of standard/common labels every resource gets |
| `<chart>.selectorLabels` (sometimes folded into `.labels`) | The subset of labels actually used for object selection |

## Why selector labels get special treatment

A `Deployment`'s `spec.selector.matchLabels` is **immutable** once the object is created — Kubernetes rejects any update that tries to change it. That makes selector labels the one part of a chart's labeling scheme you cannot casually refactor on a live release. This lesson's helper deliberately keeps a plain, hand-written `app: webapp` for selection and puts everything templated (`helm.sh/chart`, `app.kubernetes.io/*`) into a separate, non-selector `labels` helper. The exercise has you prove to yourself what happens if you don't make that distinction.
